# Receipt durability after process kill — emulator verification

**Date:** 2026-09-17
**Subject:** `DeviceSmsSender.retryPendingReceipts` / `recoverUnfinishedBatches` + `TestStore` durable receipt queue (`pending_receipts` / `sms_batches`)
**Question:** if the handset is killed (or loses data) right after the alert SMS leaves the SIM, does its receipt still land on the console — the outbox item leaving QUEUED with no operator re-queue?
**Harness:** `.github/scripts/verify-receipt-durability-kill.sh` (committed, rerunnable against any booted emulator + dev API).

## Verdict

**On this workspace's modem-less API 35 emulator, the durability mechanism is proven for every leg the hardware can produce; the two radio-dependent legs remain hardware-gated.** The primary scenario (A) is a full-fidelity kill proof: the app runs its real send path end-to-end with **no synthetic app state**, the receipt POST is deterministically on the wire when the process dies (proxy handshake, below), and the persisted receipt lands on the console after data returns. What this run does **not** prove is the radio's own behavior — this AVD's modem never registers, so the send finalizes DIVIDE_FAILED and the console outcome is DEAD_LETTER (honest failure), and the QUEUED→SENT transition plus the mid-send kill window are exercised with seeded records instead. Full-fidelity proof of those two legs (real SMS accepted by the radio, kill, resume, SENT) requires a modem-capable handset or emulator and remains open; it is tracked as the physical Pixel 11 hardware run.

| Phase | Kill window | How the state is produced | Console result | Device journal |
|-------|-------------|---------------------------|----------------|----------------|
| 0 — probe | — | real send on this AVD | DEAD_LETTER | `DIVIDE_FAILED` finalize in ~1s proves production code **cannot** leave an unfinished batch here |
| A — primary | force-stop while the app's receipt POST is in flight | **real send path only**: the proxy accepts the receipt POST and never answers, and writes a `.seen` marker naming the incident (the POST path carries `/api/cas/incidents/<id>/device-receipt`); the harness waits for a marker naming *this* incident before killing — so the kill is *provably* inside this incident's send→receipt window, not racing the posting thread and not satisfiable by a stale request | QUEUED held through the kill and through a blocked (503) resume → **DEAD_LETTER** after data returns | no `SMS_RECEIPT_OUTCOME` before the kill → `FAILED; receipt kept for retry` while blocked → `RECEIPT_RETRY_OUTCOME reported:1` → `SMS_RECEIPT_OUTCOME REPORTED` |
| B — seeded | process killed with radio results outstanding | seeded `sms_batches` record (this AVD cannot produce one — phase 0) | QUEUED → **DEAD_LETTER** | `SMS_BATCH_RECOVERY recovered:1` → watchdog `SMS_SEND_OUTCOME NO_RADIO_RESULT` → `REPORTED` |
| C — supplementary | process killed with an unaccepted all-success receipt | seeded `pending_receipts` record (needs a modem for real) | QUEUED → **SENT** | `RECEIPT_RETRY_OUTCOME reported:1` |

Every phase also asserts the durable store drains afterwards (`pending_receipts` back to `[]`, `sms_batches` back to `{}`) and that no operator re-queue was involved.

Scenario A proves the kill window itself, not just the retry: the receipt POST is deterministically still on the wire when the process dies — the proxy writes a `.seen` marker the instant it accepts the hanging POST and the harness refuses to force-stop until the marker exists, so the kill cannot have raced ahead of the posting thread (the journal also shows no receipt outcome before the kill). The console never leaves QUEUED while the receipt is undelivered — including across a blocked resume whose retry fails honestly and keeps the receipt — and the persisted state lands the moment data returns. Because the app persists the receipt before the posting thread runs, the marker-confirmed kill also proves the survivor is the pending receipt specifically, which the harness asserts.

## Scope boundary (what still needs hardware)

This container's emulated modem never registers (no `isms` service; every `SmsManager` op — including `divideMessage` — throws `UnsupportedOperationException`), so two things cannot be produced by production code here:

1. **An unfinished batch.** On a modem AVD/handset, parts dispatch and radio results can outlive the process; here the send finalizes DIVIDE_FAILED in-line. Scenario B therefore seeds a fixture generated by the production encoder itself (`scripts/receipt-durability/SeedFixtureGenerator.kt`, compiled against the real `ReceiptDurability.kt` — so the seeded bytes track the on-disk format, `cycleToken` included, instead of drifting), and phase 0 fails loudly if a future AVD ever makes the real window reachable, forcing the seeding to be re-derived.
2. **An all-success receipt (console SENT).** Scenario C seeds it (same production encoder) to prove the QUEUED→SENT transition of the retry path; the full-fidelity version (radio accepted, kill, resume, SENT) is the physical Pixel 11 run on the hardware workstation.

Everything else — the kill, the data outage, resume, `recoverUnfinishedBatches`, `retryPendingReceipts`, the real receipt POST over `adb reverse`, the console transaction, and the store draining — is the unmodified app running on a real device image.

## Method

Driver: `.github/scripts/verify-receipt-durability-kill.sh` with `CAS_FLOW_APK`, `CAS_FLOW_API_HOST`, `CAS_FLOW_DEVICE_TOKEN` (same conventions as `verify-sms-flow.sh`). Key mechanics:

- All device traffic goes through `.github/scripts/cas-receipt-gate-proxy.py` (adb reverse maps the device's port to it; it forwards to the dev API). Two flag files give two deterministic outage shapes for the receipt leg only, no race against the app's ~1 s finalize window: the **block** flag refuses `/device-receipt` POSTs with 503; the **hang** flag accepts the connection and never answers, so scenario A can force-stop the app while its receipt POST is still in flight. Removing the flags restores data. (The proxy forces `Connection: close` on every forwarded request; otherwise HttpURLConnection's keep-alive pool lets the receipt POST ride the trigger's connection and bypass the per-connection gate.)
- Seeded records go through `run-as <pkg>` into the real SharedPreferences file while the app is force-stopped (app uid, correct SELinux context; `mkdir -p` the `shared_prefs` dir on fresh install; JSON quotes XML-escaped). The seed JSON is emitted by the production encoder via `scripts/receipt-durability/SeedFixtureGenerator.kt`, compiled with the same pinned kotlinc/org.json toolchain as `scripts/test-receipt-durability.sh` (which the harness runs first, so a broken encoder fails the run before any seeding).
- Console state polled via `GET /api/cas/state`; incidents resolved between phases so each trigger creates a fresh incident.
